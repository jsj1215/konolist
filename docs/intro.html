WHY

왜 만들었나

코인 노래방은 시간이 돈입니다. 그런데 부를 노래를 고르는 시간도 그 안에 들어가 있었습니다.

😵 문제

  • 방에 들어간 뒤에야 부를 노래를 떠올리고, 기기에서 제목을 하나씩 검색함
  • 메모장 애창곡 목록에는 TJ 번호가 없어 다시 찾아야 함
  • 분위기별로 나누거나 부를 순서를 바꾸기 번거로움
  • 친구의 애창곡을 받으려면 캡처나 메시지로 주고받아야 함
➜

🎤 해결

  • 검색 결과에 TJ 번호가 바로 붙어 나오고, 한 번 눌러 리스트에 담음
  • 리스트 안에서 드래그로 순서를 정하고 곡별 메모를 남김
  • 공개 링크 하나로 공유하고, 받은 사람은 자기 보관함으로 복사
  • 노래방에서는 리스트를 열어 번호만 입력하면 끝
FEATURES

코노 갈 때 필요한 모든 것

검색부터 정리, 공유, 기록까지 하나의 앱에서.

🔍

실시간 노래 검색

제목·가수로 검색하면 TJ 노래방 번호가 자동으로 표시됩니다. 번호 외우거나 따로 찾을 필요 없습니다.

🎵

플레이리스트 관리

나만의 리스트에 노래를 담고, 드래그로 부르고 싶은 순서대로 정렬하세요. "2키 낮춰서" 같은 곡별 메모도 남길 수 있습니다.

🔗

플레이리스트 공유

내 리스트를 공개로 전환하고 링크로 친구에게 공유하세요. 받은 리스트는 내 보관함으로 복사할 수 있습니다.

📅

캘린더 방문 일기

코노 다녀온 날을 캘린더에 기록하고, 그날 부른 플레이리스트를 연결하세요. 언제 갔는지 한눈에 보입니다.

🎙️

곡별 녹음

브라우저 마이크로 바로 녹음해 곡마다 저장하고, 나중에 다시 들으며 연습할 수 있습니다.

⚡

검색 캐시

한 번 검색한 키워드는 1시간 동안 Redis 캐시에서 바로 응답해, TJ 사이트를 매번 다시 조회하지 않습니다.

비비

친구의 18번, 링크 하나로

내 플레이리스트를 공개로 바꾸면 링크가 생깁니다. 친구에게 보내면 회원가입 없이도 내 리스트를 볼 수 있고, 로그인한 친구는 버튼 한 번으로 자기 보관함에 복사할 수 있습니다.

  • 🌐 공개/비공개 전환
  • 🔗 링크로 간편 공유
  • 📥 내 보관함으로 복사
ARCHITECTURE

시스템 구성

Next.js 프론트엔드와 Spring Boot REST API를 분리하고, 외부 사이트 크롤링 앞에 Redis 캐시를 두었습니다.

App Router 페이지 + NextAuth Credentials provider. 로그인 시 백엔드 /api/auth/login을 호출해 받은 JWT를 세션에 보관
REST / JSON ⇄

Stateless Spring Security + JWT 필터, 도메인별 패키지 구성

🐘 PostgreSQL

🕷️ tjmedia.com

💾 로컬 디스크

🔍 노래 검색 한 번에 일어나는 일

  1. 요청 — GET /api/songs/search?q=아이유 (비로그인 허용, 1~50자 검증)
  2. 캐시 조회 — 검색어를 소문자·공백 정리해 song:search:아이유 키로 Redis 조회
  3. 히트 — 저장된 JSON을 그대로 반환
  4. 미스 — Jsoup으로 TJ 검색 페이지를 가져와 CSS 셀렉터로 번호·제목·가수를 파싱하고 TJ 번호 기준으로 중복 제거
  5. 저장 — 결과가 있을 때만 TTL 1시간으로 캐시. 크롤링 실패로 빈 결과가 나오면 캐시하지 않아 다음 요청에서 다시 시도
DESIGN DECISIONS

설계하면서 내린 결정

각 결정의 이유와 함께, 감수한 비용도 적었습니다.

01

곡 마스터 테이블 대신 캐시 + 비정규화

결정
검색 결과는 Redis에만 1시간 보관하고, 리스트에 담을 때 TJ 번호·제목·가수를 playlist_songs에 복사
이유
TJ 전곡을 받을 공식 API가 없어 곡 마스터를 정확히 유지하기 어려움. 담은 곡은 원본 사이트가 바뀌어도 남아야 함
비용
Redis 장애 시 검색 실패. TJ 마크업이 바뀌면 셀렉터 수정 필요
song/SongSearchService.java
02

@Cacheable 대신 StringRedisTemplate

결정
캐시 조회·저장을 코드로 직접 작성
이유
크롤링 실패로 빈 리스트가 나왔을 때 그 결과를 1시간 동안 캐시해 버리는 일을 막기 위함
비용
직렬화·예외 처리 코드를 직접 관리. 역직렬화 실패 시 재크롤링으로 폴백
song/SongSearchService.java
03

공유 URL은 UUID 토큰 + 공개 여부 이중 확인

결정
생성 시 수정 불가 shareToken(UUID) 발급. 조회·복사는 토큰으로 찾은 뒤 isPublic일 때만 허용
이유
순차 ID를 쓰면 번호만 바꿔 남의 리스트를 열 수 있음. 비공개로 돌리면 같은 링크가 즉시 막힘
비용
토큰 재발급 기능이 없어 퍼진 링크는 비공개 전환으로만 차단
playlist/Playlist.java, PlaylistService#getByShareToken
04

JWT는 Spring이 발급, NextAuth는 보관만

결정
백엔드가 BCrypt로 비밀번호를 검증하고 JWT 발급. NextAuth Credentials provider가 이를 호출해 세션에 저장
이유
인증 규칙과 사용자 데이터는 백엔드 한곳에 두고, 프론트는 NextAuth의 세션 관리만 활용
비용
토큰 만료 24시간, 리프레시 토큰 없음. NextAuth 세션도 24시간으로 맞추고, 401을 받으면 로그아웃 처리
common/config/SecurityConfig.java, api/auth/[...nextauth]/route.ts
05

인가는 서비스 계층의 소유권 검사로

결정
Security 설정은 인증 여부만 확인. 리스트·곡·녹음·기록 접근 시 서비스에서 소유자를 비교하고 아니면 403
이유
"내 리소스인가"는 URL 패턴으로 판단할 수 없음. 곡은 findByIdAndPlaylistId로 소속 리스트까지 확인
비용
검사 코드와 예외 핸들러가 서비스·컨트롤러마다 중복
PlaylistService#getPlaylistWithOwnerCheck
06

순서 변경은 전체 ID 배열 덮어쓰기

결정
드래그 직후 화면 순서를 먼저 바꾸고, 전체 곡 ID 배열을 PATCH /songs/reorder로 전송. 서버는 인덱스를 sortOrder로 저장
이유
리스트당 수십 곡 규모라 전체 덮어쓰기가 가장 단순하고 정렬 키 충돌이 없음
비용
곡 수만큼 UPDATE 발생. 저장 실패 시 화면 롤백 없음
PlaylistService#reorder, playlists/[id]/page.tsx
DATA & API

데이터 모델과 API

🗂️ 엔티티 (JPA)

users
email (unique) · password (BCrypt) · nickname · created_at
playlists
user → users · title · description · is_public · share_token (UUID, unique) · created_at · updated_at
playlist_songs
playlist → playlists · tj_number · title · artist · memo · recording_path · sort_order
calendar_logs
user · date · playlist — (user_id, date, playlist_id) 유니크 제약

리스트를 지우면 곡도 함께 삭제됩니다 (cascade = ALL, orphanRemoval). 같은 리스트에 같은 TJ 번호는 한 번만 담을 수 있습니다.

SECURITY

보안 설계

🛡️ 적용한 것

  • 비밀번호는 BCrypt 해시로만 저장, 로그인 실패 메시지는 이메일·비밀번호 구분 없이 동일
  • Stateless 세션, 매 요청 JWT 서명 검증 후 SecurityContext 설정
  • 인증 없이 열린 경로는 로그인/회원가입, 노래 검색, 공개 리스트 조회 세 가지뿐
  • 모든 쓰기·조회는 서비스 계층에서 소유자 확인, 위반 시 403
  • CORS는 localhost:3000과 FRONTEND_URL만 허용
  • JWT 시크릿은 기본값 없이 필수. 비었거나 32바이트 미만이거나 change-me로 시작하면 기동 실패
  • 토큰이 없거나 만료되면 401, 프론트가 받으면 로그아웃 처리
  • 공유 링크는 전용 DTO로 곡 번호·제목·가수·순서만 공개 (메모, 녹음 여부, 내부 ID 제외)
  • 녹음은 오디오 형식만, 파일당 20MB까지. 경로는 서버가 정한 ID로만 만들고, 곡·리스트 삭제 시 파일도 정리
  • Next.js 보안 헤더(nosniff, 프레임 금지, 마이크만 허용하는 Permissions-Policy)
  • 시크릿은 환경변수로 주입, .env와 녹음 파일 디렉터리는 Git에서 제외

⚠️ 알고 있는 한계

  • 리프레시 토큰이 없어 24시간 뒤 재로그인 필요
  • 로그인과 노래 검색에 요청 횟수 제한이 없음
  • 녹음 파일이 로컬 디스크에 있어 서버를 늘리면 공유 스토리지가 필요
  • 카카오 로그인은 기획에만 있고 현재는 이메일/비밀번호 방식
GET STARTED

로컬에서 실행하기

Java 21, Node.js 20.9+, PostgreSQL, Redis가 필요합니다.

🍃 Backend

cd backend
cp .env.example .env
# JWT_SECRET 채우기: openssl rand -base64 48
./mvnw spring-boot:run   # :8080, .env 자동 로드

./mvnw test              # 16개, H2로 실행 (DB·Redis 불필요)

DB·Redis 값이 없으면 로컬 기본값(PostgreSQL konolist DB, 로컬 Redis)으로 실행됩니다. 테이블은 JPA가 자동 생성합니다.

⚛️ Frontend

cd frontend
cp .env.local.example .env.local
# NEXTAUTH_SECRET, NEXT_PUBLIC_API_URL 채우기
npm install
npm run dev              # :3000

npm run lint

Next.js는 .env.local을 자동으로 읽습니다.
